# RAG 面试追问：文档切分与两级 id

日期：2026-08-14
对应项目：城市安全隐患分析平台

## 一句话主回答

> 当前知识库是短文本，采用“一行动一个向量、MySQL id 即 Milvus doc_id”的简单模型；如果未来接入长文档，会引入 chunk 层：chunk_id 作为向量主键，case_id 保留业务关联，命中 chunk 后按 case_id 回查 MySQL 完整记录。

## 追问 1：为什么当前不做切分？

回答：

- 当前 tb_hazard_case 种子数据 42 条，每条描述 50-150 字，属于短文本。
- 一行一个向量足够：embedding 一条短文本不会丢失细节，检索命中即整条记录。
- 切分是为长文档服务的，当前引入只会增加同步、去重和回查复杂度，属于过度设计。

## 追问 2：如果接入长文档，切分方案怎么设计？

回答：

- 两级 id：
  - case_id：业务 id，对应 MySQL 里那条案例/法规；
  - chunk_id：向量库主键，唯一标识某一段，例如 `case_123_chunk_0`。
- 向量库字段：chunk_id、case_id、chunk_index、content_hash、embedding。
- 关系：一个 case_id 对应多个 chunk_id。
- 检索流程：向量检索命中 chunk -> 拿到 case_id -> 按 case_id 回 MySQL 查完整记录 -> 片段 + 完整记录一起给模型。

## 追问 3：切分粒度怎么选？chunk size 和 overlap？

回答：

- 取决于文档类型和 embedding 模型上下文上限，通常 300-500 字一段，overlap 50-100 字。
- 法规条文这类结构化文本按条切分，比固定字数更合理。
- 最终标准是评估集上的召回质量，而不是某个固定数字。

## 追问 4：命中多个 chunk 怎么去重和排序？

回答：

- 按 case_id 聚合：同一案例命中的多个 chunk 合并，避免报告重复引用。
- 排序先按相似度，必要时用 RRF（Reciprocal Rank Fusion）融合向量和关键词排名，或加交叉编码重排。

## 追问 5：内容更新和删除怎么办？

回答：

- content_hash 按 chunk 内容计算，某一段变了只重新算那一段的 embedding。
- 案例删除时，按 case_id 删除它对应的所有 chunk。

## 追问 6：如何证明切分真的有效？

回答：

- 构造小型评估集：查询-期望命中文档-期望报告要点。
- 对比切分前后召回率、命中位置和报告引用准确性。
- 用失败样本反推 chunk 大小和 overlap 是否合理。

## 面试提醒

- 不要承诺项目“已经实现切分”，当前项目没有实现。
- 用“当前短文本不需要，长文档时我会这样设计”的表达，展示架构取舍能力。
