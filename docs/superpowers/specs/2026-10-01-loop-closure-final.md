## 0. 先把"闭环"定义清楚

否则"还差什么"永远说不完。四条判据，缺一不算闭环：

| # | 判据 | 意思 |
| --- | --- | --- |
| **A** | **产物正确** | 每一类输入 → 该给的那种产物。不出现"用户问判断，系统给报告" |
| **B** | **路径完整** | 每条分支都有落点、都能结束、不留半启动状态 |
| **C** | **可验证** | 每条结论要么有测试、要么有实测数字 |
| **D** | **可交付** | 提交、部署、线上验过、能讲清楚 |

## 3. 必须改的：只有两条

> 判据：**不改就会持续产出错误产物**，或**不改就没法交付**。
> 其余全部归入 §5「登记不做」。

### M1 —— 路由的判据从"模型这一轮说了什么"换成"代码可判的信号"

**它一次解掉 #1 和 #3 的大半。**

现状：`route` 走哪个节点，取决于规划器这一轮吐的 `intent`。而它 10 次 4 种 —— **产物就跟着飘**。

改法：判据全部换成**代码能判的东西**，`intent` 从"开关"降级成"信号"（只影响措辞与是否追问，不再决定产物）：

| 产物 | 判据（全部代码可判，且多数是**已有常量**） |
| --- | --- |
| 应急指引 | `danger_veto`（词表 + 模型，双保险，保留） |
| 完整报告 | 用户原话命中 `REPORT_PHRASES`（"查法规/出报告/详细报告/帮我查"…，**已存在**） |
| 纯回答 | 命中 `CASUAL_JUDGMENT_PHRASES`（"算不算/是不是/危险吗/严重吗"…，**已存在**，现在叫 `_is_casual_judgment`） |
| 初步判断 + 追问 | 以上都没命中，且 `missing`（A 类缺口）非空 |
| 完整报告（兜底档） | 以上都没命中，且 `missing` 为空 |
| 寒暄 / 越界 | `direct_mode`（已有，词表 + 模型） |

**再加一条"模式继承"**，专门解省略句（"那 X 呢"）：

> 上面几条都没命中时，**沿用上一轮的产物模式**；会话第一轮没有上一轮，才按 `missing` 判。

**为什么这样能闭环**：

- "那广告牌呢" → 不命中任何切换词 → **沿用上一轮（纯回答）** ✓（今天：6/10 会走报告 ✗）
- "帮我查广告牌的法规" → 命中 `REPORT_PHRASES` → 切报告 ✓
- 危险 → 第 1 条先命中 → 应急指引 ✓
- 用户在描述隐患（首次）→ 按 `missing` 判 → 齐全出报告、缺则追问 ✓

**关键**：`intent` 飘不再致命 —— 它只影响措辞。

### M2 —— 补危险词表

`DANGER_TERMS` 补上"正在燃烧 / 燃烧 / 黑烟 / 明火 / 烧起来 / 火势"这类说法。

- 成本：一个元组加几个词 + 一条单测
- 为什么必须：危险是**唯一**能压过一切的通道，它只剩一道防线（模型）是不可接受的
- 顺带把这条测出来的场景做成回归用例

## 4. M1 的代价与边界（说清楚，别过度承诺）

- **代价**：`route` 的性质变了 —— 从"翻译模型的话"变成"按代码信号分发"。这**更符合你们早就立的"route 只做映射、决策权只有一处"**，但它会动 `dialogue_policy` 的判据（`_question_for_missing` 那几处也在里面，跟 spec 决策 4 是同一处）
- **边界**：M1 只保证**产物确定**。**指代解析（"那那个呢"）仍然靠模型** —— 那一半提高有上限，实测纯指代型 `perceived_subcategory` **0/4 给出**（只能靠 `issues` 兜底）。**不承诺完美。**
- **不做的事**：不为 M1 新增 state 字段之外的机制；不引入新的模型调用

## 5. 登记不做（明确列出来，免得又变成待办清单）

| 项 | 为什么不做 |
| --- | --- |
| 决策 9 的"C 规则"（候选唯一才兜底） | 只在**同大类**抢锁时才有意义；实测不同大类 0/3 被污染。**先不做，等 M1 落地后重测** |
| 决策 10"模式锁"独立字段 | **被 M1 吸收** —— 继承只是 M1 判据表里的一条，不需要单独字段 |
| 情况二（未答追问就换话题） | **产品规则，不是技术问题**，需要人拍板；M1 不解决它 |
| `find_negated` 复活 / `relationship_hint` 启用 | 死字段，先留着不动 |
| JEV 决策模型 | 已登记为"待评估"，不开工作项 |
| 紧急/寒暄/越界三条路径本身 | 已经是要的形状 |

## 6. 参考（网上查到的，都标了出处）

1. **结构化输出的稳定性是可以量化、且必须在生产前量化的**
   *STED and Consistency Scoring: A Framework for Evaluating LLM Structured Output Reliability*, arXiv:2512.23712
   —— 核心结论：**对同一次生成重复采样，量化一致性**；且**不同模型的稳定性差异巨大**（Claude-3.7-Sonnet 在 T=0.9 仍近完美，Haiku/Nova-Pro 明显退化）。
   → 对应我们的实测：同一句话 10 次 4 种 `intent`。**这不是我们的实现问题，是必须被测量的生产指标。**

2. **"刚性 JSON schema"本身会降低可靠性 —— 要给字段写含义**
   *Meaning Typed Prompting (MTP)*, arXiv:2410.18146
   —— 核心结论：把**类型 + 含义 + 抽象**写进提示词，比只给 rigid JSON schema 更可靠。
   → 对应我们做对的与做错的：给 `perceived_subcategory` 写了三段含义 → 10/10 稳；`intent` **只列了 7 个标签名、没给判据** → 10 次 4 种。**这是同一实验里的对照。**

3. **指代消解是任务型对话的已知难点，业界做法是"让模型对元数据 + 对话历史做显式推理"**
   *Reasoning over Object Descriptions Improves Coreference Resolution in Task-Based Dialogue Systems*, arXiv:2604.27850
   —— 核心结论：test-time reasoning + 结构化元数据 + 提示词工程，跨域泛化优于监督模型。
   → 对应我们的边界：**指代这一半只能提高、不能保证**，方向是"给模型结构化元数据让它推"，而不是代码猜位置。

**没拿到的**：LangGraph / OpenAI / Anthropic 官网文档在这台机器上**连不上**（SSL 被拦），所以没有官方来源。上面三条是 arXiv，可自行核。

## 7. 一句话结论

**闭环只差两条：M1（路由判据换成代码可判的信号 + 模式继承）、M2（补危险词表）。**
其余全部是"已知、不阻塞、登记不做"。

M1 之后，`intent` 飘不再影响用户看到什么 —— 这条线就可以停了。
