# 检索自评重试环（evaluator-optimizer）

日期：2026-09-27
状态：待执行
关联：`core/assistant_graph.py`、`core/uncertainty.py`、`core/case_relevance.py`、`tools/hybrid_search.py`

## 1. 为什么要写这个环（两个理由，分开算账）

1. **架构完整性**：这是编排模式清单里我们唯一缺的 workflow 模式。缺了它，面试里"我刻意不上 ReAct"
   听起来像"我不会写循环"。
2. **它对应一个真实的、已被证实的失败模式**：检索串不是用户原话，而是 `_pick_keyword(小类, 槽位)`。
   所以"检索不相关"的唯一来源是**槽位抽错/抽到幻觉词**，重试正好修这个。

**明确不成立的触发条件**：不能用"召回低"。当前实测 Hit@5 在槽位空/槽位有值两种情形都是 **1.000**
（`db/eval_retrieval_output.txt`），基于召回的触发率会是 0，写了就是死代码。

## 2. 触发条件（三条，全部来自已有实测）

判定**由代码做**（可验证信号），不用模型自己说"我要重试" —— 否则环不可测。

| # | 条件 | 依据 | 预期触发率 |
| --- | --- | --- | --- |
| T1 | `ungrounded_slots` 非空（槽位值在原文里找不到依据） | `core/uncertainty.py` 已有的信号；接地实测 8/8 | 待测 |
| T2 | 检索结果与锁定大类的交集为空（`filter_by_major` 返回 `NO_MATCH`） | 最硬的"检索失败"信号 | 待测（`other`「其他」最易触发） |
| T3 | top1 向量分数落进灰色带 `[RETRIEVAL_MIN_SCORE, WEAK_SCORE)`，建议 `WEAK_SCORE = 0.58` | 实测 p10 = 0.5426（法规）/ 0.5726（案例），说明约 10~20% 查询落带内 | 待测，预计 10~20% |

任一条成立即触发。

## 3. 图形状（有界）

```
retrieve ×2 ──reducer──▶ evaluate_retrieval
                              │  代码判定，规则纯函数、可测
                 ┌────────────┴────────────┐
                 ▼                         ▼
        不达标 且 attempts<1            达标 / 已重试过
                 │                         │
                 ▼                         ▼
          rewrite_query ──▶ search       report
        （模型产出新检索串）  attempts+1
```

不变式（必须写成测试）：

1. **`retrieval_attempts >= 1 时不得再进 `rewrite_query``** —— 环有上界。
2. **不触发时不得增加任何 LLM 调用** —— 延迟不能因为"架构完整"而变差。
3. `rewrite_query` 产出的检索串**必须仍然是"标签 + 槽位值"的形状**（`_pick_keyword` 的契约），
   不能变成自然语言长句 —— 否则关键词分支又会退化成 0 命中。
4. 重试**只重试检索，不重跑分类**。分类（`locked_major`/`locked_subcategory`）在环内不得改变。

## 4. 可观测性（这个环的价值一半在这里）

每次触发必须记录：

- 触发原因（T1/T2/T3 哪个）
- 重试前 top1 分数 → 重试后 top1 分数
- 重试是否改变了最终 top1

落进 `state["retrieval_retry_log"]`，并在评测脚本里汇总。
**没有这组数据，这个环就无法证明有用，也不该上线。**

## 4.5 触发率实测（2026-09-27，只读测量，未改生产代码）

口径：32 个小类 × 2 情形（槽位空 / 槽位有值-schema键）× 2 张表 = 128 次检索，
`WEAK_SCORE = 0.58`。原始输出：`ai-module/db/eval_retry_trigger.txt`。耗时 283 秒。

| 表 | n | T2 同大类空 | T3 落灰色带/无结果 | 并集（真实触发率） |
| --- | --- | --- | --- | --- |
| `tb_hazard_case` | 64 | **0 (0.0%)** | **5 (7.8%)** | **5 (7.8%)** |
| `tb_regulation` | 64 | 2 (3.1%) | 3 (4.7%) | 3 (4.7%) |

触发明细（去重后约 4 个小类）：

| 情形 | 小类 | 表 | 现象 |
| --- | --- | --- | --- |
| 槽位空 | `illegal_structure` | case | top1 = 0.5754（贴灰色带） |
| 槽位空 | `scaffold_guard` | case | top1 = 0.5779 |
| 槽位空 | **`other`「其他」** | case | **完全无结果** |
| 槽位空 | **`other`「其他」** | regulation | **无结果 + T2** |
| 槽位空 | `illegal_wiring` | regulation | top1 = 0.5305 |
| schema键 | `scaffold_guard` | case | top1 = 0.5639 |
| schema键 | **`other`「其他」** | case | **完全无结果** |
| schema键 | **`other`「其他」** | regulation | **无结果 + T2** |

四条结论：

1. **验收标准第 1 条（触发率 > 0）成立**，且落在预期量级（预测 10~20%，实测 7.8% / 4.7%）。
2. **T3 是主力**（8 次触发里 6 次靠它）；**T2 只在法规 + `other` 上触发**，
   所以 T2 单独不足以支撑这个环，但它抓的是最硬的失败（空结果）。
3. **`other`「其他」是最严重的退化小类**：两张表、两种情形全是空结果。
   它是兜底类，向量分数天然低 —— 这个环恰好能救它，这也是最值得展示的用例。
4. 4 次触发里有 **4 次是"完全无结果"**（case 2 次 + regulation 2 次），
   即"连一条都没返回"—— 这是重试最有可能改善的情形（重写检索串后至少能拿到东西）。

**阶段 1 结论：不停止，继续实现。** 触发率非 0，环不会变成死代码。

## 4.6 实现与对照实测（2026-09-27，已写进 core/assistant_graph.py）

判定在 `should_retry_retrieval`（纯函数，不联网）；改写在 `rewrite_query`（模型）。
8 个触发点走生产代码 + 真实模型重跑，原始输出 `db/eval_retry_effect.txt`
（脚本 `db/measure_retry_effect.py`，只读）。

| 触发点 | 原因 | 触发前 top1 | 重试后 top1 | 结果块 |
| --- | --- | --- | --- | --- |
| 槽位空 illegal_structure case | T3 灰色带 0.5755 | 0.5754 | **0.6520** | 4 → 5 |
| 槽位空 scaffold_guard case | T3 灰色带 0.5779 | 0.5779 | **0.6122** | 5 → 5 |
| 槽位空 other case | T3 无语义命中 | 无 | **0.5454** | 3 → 5 |
| 槽位空 other regulation | T2 跨大类 | 无 | **0.5169** | 3 → 4 |
| 槽位空 illegal_wiring regulation | T3 灰色带 0.5305 | 0.5305 | **0.6456** | 3 → 3 |
| schema键 scaffold_guard case | T3 灰色带 0.5639 | 0.5639 | **0.6152** | 5 → 4 |
| schema键 other case | T3 无语义命中 | 无 | **0.5819** | 3 → 5 |
| schema键 other regulation | T2 跨大类 | 无 | **0.5372** | 3 → 5 |

汇总：**8/8 在代码路径里重新触发，8/8 有改善**；top1 均值（无命中记 0）**0.2810 → 0.5883**；
**触发前向量分支 0 命中的 4 个用例（都是 other）重试后全部拿到向量命中**。
跑了三遍，模型改写的词每次略有不同（例如 other 一次给「危化品 无主异味桶」、
一次给「其他 危化品桶」），但“8/8 有改善”三次都成立。
改写的词都取自用户原话里已有的具体名词（「危化品桶」「阳光房」「栏杆缺失」），
不是平空编出来的场景。

### 代价与开关

- 判定 top1 分数需要另跑一次向量检索（分数不在检索文本里），单次实测 **~0.94s**（embedding 占大头）。
  两张表**并发**取，所以整轮约 **+0.9s**（而非 +1.9s）；只在“确实有结果块”时才发。
- `PROBE_TOP1_SCORE = False` 可整个关掉探测（零额外成本），代价是灰色带那 4 个触发点不再触发，
  只剩 T1 / T2 / 完全无结果 / 无语义命中。
- `RETRY_ENABLED = False` 则整个环关掉。本次**保留启用**（见下方限制）。

### 实现上踩到的坑（已修）

LangGraph 按**节点参数的注解**过滤节点输入：节点参数注解成基类 `AssistantState` 时，
只在子类 `AssistantGraphState` 里声明的新通道在节点里读到 **None**——于是
`retrieval_attempts` 永远是 0、环不收敛。读这些通道的节点（`plan_retrieval` /
`evaluate_retrieval` / `rewrite_query`）必须注解成 `AssistantGraphState`。
`tests/test_retrieval_retry.py` 里的端到端图用例就是这个坑的回归锁（不收敛会直接
GraphRecursionError）；另外图的步数上限从默认 10007 收紧到 60，万一以后又失效，
是快速报错而不是烧掉千次模型调用。

### 已知局限

- 槽位 fixture 是合成的（见 `eval_retrieval.py` 说明），不是规划器真实输出；
- 重试收益依赖模型改写质量，且每个触发点只跑一次，**没有方差数据**（三遍全量都是 8/8）；
- 上线前还没在真实多轮对话里跑过（部署验证留给下一步）。

## 5. 验收标准（不达标就默认关闭）

1. 在 64 条评测集上跑，**触发率 > 0**，并报告 T1/T2/T3 各触发几次。
2. 触发后 **top1 分数有提升**（哪怕只提升一部分）。提升为 0 则撤掉优化、保留环但默认关闭。
3. `retrieval_attempts` 上界有单测锁；不触发路径无额外 LLM 调用（用 fake 计数）。
4. 全量 pytest 通过（既有失败 `tests/test_vector_delete_api.py` 除外）。
5. 端到端延迟：触发路径最多增加 1 次模型调用；不触发路径延迟不变。

## 6. 明确不做的事

- 不让模型决定"要不要重试"（只让它决定"怎么改写"）。
- 不做多轮重试（上界 1）。
- 不重跑分类、不改锁定大类。
- 不改前端（状态文案已有契约；如新增状态，补进 `STATUS_TEXT` 并过 `tests/test_status_text.py`）。
- 不修 `tests/test_vector_delete_api.py`。
