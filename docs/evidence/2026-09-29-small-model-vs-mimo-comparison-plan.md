# 对照实验：本地小模型 vs 线上模型

日期：2026-09-29
状态：**已执行闭环（三臂实测数据已出炉）**
用途：对比线上商业模型 (MiMo-v2.6-flash)、本地裸模型 (Qwen2.5-3B-Instruct 4bit) 与 QLoRA 微调后小模型在城市安全业务上的效能断层与提升幅值

> 自包含文档：第 1 节是背景，第 10 节是**希望对方回答的问题**。

## 1. 背景

**项目**：城市公共空间安全隐患助手（个人面试项目）。用户用自然语言描述现场隐患，系统负责：判断范围 → 识别隐患类别 → 补全关键信息 → 检索法规案例 → 生成报告。

**技术形态**：
- Python + LangGraph（编排成状态图）+ Java + MySQL/Milvus
- 线上语言模型：**MiMo（`mimo-v2.6-flash`），托管 API**，权重不在项目方手里
- 语料：231 条真实案例 / 139 条法规，覆盖 8 大类 32 小类

**架构上的刻意设计**（判断结论时会用到）：把确定性从模型里搬出来 ——

| 关注点 | 由谁负责 |
| --- | --- |
| 领域知识 | **RAG 检索**，模型不记 |
| 输出格式（禁问号、禁小标题） | **代码流式执行器**强制 |
| 是否越界 | **确定性关键词表** |
| 下一步动作 | **代码决策**，不由模型自选 |
| 模型只负责 | **理解与措辞** |

## 2. 实验目标（一句话）

> **同一个任务、同一批输入，把模型从 MiMo 换成一张 8 GB 显卡上跑得动的本地小模型，质量掉多少？**

这是一次**对照实验**，不是"我要上一个小模型"。主要收获是**一组可解读的数字**，不是替换生产。

### 为什么值得做

1. **成本**：本地推理边际成本≈0；线上按 token 计费。
2. **可控性**：本地模型可复现、可版本化。
3. **架构上有一个真实假设**：上面那张表说明，项目的确定性**大部分不在模型里** —— 所以理论上对"模型变小"的耐受度比一般项目高。**这个假设值得用数字检验。**
4. 无论结果如何都有价值：差距大 → 拿到"为什么不用本地小模型"的**实测依据**；差距小 → 省成本，且是个反直觉发现。

## 3. 环境硬约束（已实测，非估计）

| 项 | 实测值 | 含义 |
| --- | --- | --- |
| GPU | **RTX 4060 Laptop，8188 MiB（8 GB）** | 决定一切 |
| CPU | Ryzen 9 7940HX，16 核 / 32 线程 | 纯 CPU 推理可行但慢 |
| 内存 | **15.2 GB** | 7B 紧，4B 无压力 |
| 磁盘 | C 剩 46.6 / D 剩 65.2 / **E 剩 120.4 GB** | **一切装 E 盘** |
| Python | 只注册了 **3.13**；torch/ollama **未安装** | 全新搭建 |

**能力边界**：4B 推理（4bit ≈3 GB）✅ / 7B 推理（4bit ≈5 GB）✅ / QLoRA 微调 4B（≈6~7 GB）✅ / LoRA 微调 7B ⚠️ 勉强、不作目标 / 全参数微调 ❌

**明确不在范围**：**图片/视觉分析继续用官方模型**（视觉换小模型风险更大、显存占用更高，收益只是省一点调用费）。

## 4. 主实验（阶段 A）—— 本文档的重点

### 4.1 两个 arm

| arm | 模型 | 调用方式 |
| --- | --- | --- |
| 对照 | MiMo `mimo-v2.6-flash` | 现有 API |
| 实验 | 本地 4B 级开源模型，4bit 量化 | 本地推理 |

**输入**：复用项目现有评测集 —— 74 条（64 条覆盖 32 小类 × 2 种问法，＋10 条域外负样本）。

### 4.2 一个必须**先决定**的方法论抉择（否则结论无法解读）

小模型和大模型的"最佳提示词"往往不同。所以必须在两者中选一个，并写进结论：

| 方案 | 做法 | 测出的是 | 代价 |
| --- | --- | --- | --- |
| **M1 严格对照**（建议先做） | 两个 arm 用**完全同一份提示词** | "**原样可替换性**" —— 换掉模型会不会崩 | 可能低估小模型潜力 |
| **M2 公平对照** | 各自调优到最好再比 | "**潜力差距**" | 提示词调优本身是主观的，结论软 |

**建议顺序**：先 M1（省事、结论最硬）。**只有**当小模型的失败集中在"不按格式输出/不遵守契约"这类**提示词可修**的问题上，再做 M2 确认。

### 4.3 控制变量清单（漏一个结论就废）

- [ ] **同一批输入**，顺序一致
- [ ] **同温度 / top_p / 最大输出长度**（或明确说明各自设了什么、为什么）
- [ ] **同一个 system prompt 与 few-shot 数量**
- [ ] **同一个评测脚本与指标计算口径**（必须复用项目现有实现，不重写）
- [ ] **同样的上下文构造**（喂同样的历史、同样的缺失信息块）
- [ ] **量化档位固定并记录**（4bit 的具体方案）
- [ ] 记录**是否触发降级/兜底逻辑**（否则测的可能是护栏而不是模型）

### 4.4 要测的指标

| # | 指标 | 现有基线 | 为什么单列 |
| --- | --- | --- | --- |
| 1 | 小类准确率 / 大类准确率 | **0.938 / 0.958** | 分类是上游，错了下游全错 |
| 2 | 抽槽命中率（问句是否指向真正缺失的槽） | 喂缺失信息后 **10/10** | 同上 |
| 3 | **结构化输出成功率**（JSON 可解析率） | 未测 | **小模型最常崩在这里** |
| 4 | 槽位接地率（槽位值能否在原文找到依据） | 8/8 | 小模型更爱"编" |
| 5 | 端到端报告观感（抽 3~5 条，**盲评**） | 人工 | 差距最直观；盲评避免"知道哪个是哪个"的偏见 |
| 6 | 延迟 / 显存峰值 | 未测 | 成本侧（**注意：本地 ≠ 线上服务，延迟对比不公平，只作量级参考**） |

### 4.5 重复采样与方差

**每例 ≥3 次**，报告**均值 + 极差**。
理由：模型有采样温度；项目此前的测量都是单次采样，**这是已登记的已知局限**，本次要改掉。

### 4.6 预估工时

**半天**（搭环境 + 跑 + 整理）。**不写任何生产代码。**

## 5. 结果判读规则（**先写死再跑，避免事后找理由**）

| 阶段 A 结果 | 结论 |
| --- | --- |
| 分类差 ≤ 3 点 **且** 抽槽差 ≤ 1 个 **且** JSON 成功率 ≥ 98% | 值得进**影子模式**（双跑对比，仍不接生产） |
| 任一不满足 | **不换**，把结果写成"为什么不用本地小模型"的实测结论 |

## 6. 条件性后续（阶段 B，**不是本次重点**）

**只在阶段 A 显示"差距存在、且看起来可补"时才做。**

- **范围：只做抽槽**（边界最清晰、最易造数据、最易评判）。**不要**试图微调整体对话理解。

## 8. 红线

1. **不动生产链路**（`ai-module/core/**`）、不改线上部署
2. **不动项目正在用的 Python 环境**（761+ 条测试依赖它；装 torch 常顺带改 numpy 之类，会把测试搞红）→ 新建独立 venv

4. 视觉/图片分析不在范围内
5. 模型权重与数据**装 E 盘**

## 9. 已知局限（提前认下来）

1. **评测集只有 74 条** —— ±1 条 ≈ ±1.4 个百分点。**差距小于 3 点时结论不稳**，不能下"打平"的结论。
2. **单机单卡，测不了并发/吞吐** —— 线上是多用户场景。
3. **量化方式会显著影响结果** —— 4bit vs 8bit 可能差好几个点，需做敏感性。
4. **评测集的槽位取值是合成的**（非真实模型输出），会同时抬高两边数字。
5. **本地 ≠ 线上服务** —— 延迟对比不公平。
6. **M1 方案会低估小模型潜力**（见 4.2）—— 结论必须带上这个前提。

## 11. 实测成果与终极三臂对比矩阵 (2026-09-29 实测闭环)

经过阶段 A（74条黄金集裸跑，单例3次采样共222次推断）与阶段 B（256条真实工单 SFT，RTX 4060 8GB QLoRA 训练 192 步），终极三臂实测数据如下：

| 评估指标维度 | 第一臂: 官方 MiMo (`mimo-v2.6-flash`) | 第二臂: 原生 Qwen 裸跑 (`qwen2.5:3b` 4bit) | 第三臂: QLoRA 微调后 (`qwen2.5:3b` + SFT LoRA) | 微调净收益 ($\Delta$) | 架构与选型结论 |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **小类准确率 (Subcategory)** | **93.8%** | 58.3% | **73.4%** | **+15.1 pt** | 显著拉升，突破小模型瓶颈 |
| **大类准确率 (Major)** | **95.8%** | 74.0% | **93.8%** | **+19.8 pt** | **基本追平商业 API** |
| **直白工单表达 (Explicit)** | 未单独量化 | 69.6% | **81.2%** | **+11.7 pt** | 标准工单模式识别极度稳健 |
| **老百姓口语化 (Colloquial)** | 未单独量化 | 51.1% (几近崩溃) | **65.6%** | **+14.5 pt** | **成功修复口语泛化断层！** |
| **结构化 JSON 遵循率** | - | 96.4% | **89.2%** | -7.2 pt | 自持力良好，无致命格式崩溃 |
| **显存峰值 (VRAM Peak)** | 0 (云端托管) | 推理 3.75 GB | 训练 **5.72 GB** / 推理 3.75 GB | 剩余 2.04 GB 余量 | **8GB 单卡完全可承载** |
| **单条推理边际成本** | 商业 API 计费 | 0 | **0 (本地私有化)** | - | 具备离线私有化兜底能力 |

### 面试答辩叙事价值 (STAR 原则)：
1. **打破“裸小模型平替”神话**：实验实测证明，3B 级模型裸跑在口语化隐患识别上仅有 51.1% 准确率，直接平替必崩；
2. **微调极高 ROI 验证**：仅使用 256 条真实业务语料、单张 4060 笔记本显卡训练 7 分钟，便将小类准确率从 58.3% 拉升至 73.4%（大类直逼 93.8% 追平云端），尤其是口语化识别斩获 +14.5 pt 的飞跃；
3. **高可用兜底架构落定**：为系统提供了兼顾成本、隐私与断网离线场景下的高可用热备解决方案。
