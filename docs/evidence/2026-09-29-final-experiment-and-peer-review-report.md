## 1. 项目业务背景与核心问题

### 1.1 业务形态
* **应用系统**：城市公共空间安全隐患助手（政务治理/网格巡查辅助决策系统）。
* **用户输入**：现场群众或网格员用自然语言描述现场隐患（例如：“楼道里全是废旧自行车和纸箱，过道走不过去还堵着消防箱”、“消火栓水阀滑丝关不上无法联动”）。
* **系统职责**：
  1. **意图判断与范围界定**：识别是否为 8 大类 32 小类法定隐患，域外违规即时拦截；
  3. **细分类别判定与槽位提取**：主工程的规划器契约是 `issues[].major_code / subcategory_code`，外加 `slots / question / question_target / premises_scope / intent / needs_search` 等字段；（本实验为压缩变量，在小模型侧改用**简化契约** `{"major": string, "subcategory": string}`，见 §3）；
  3. **信息补全追问**：判定关键信息缺失并生成追问；
  4. **知识增强**：基于 RAG 检索 139 条法定规章与 231 条真实处罚案例；
  5. **报告生成**：生成标准化行政通报与整改督办单。
* **现有架构**：Python (FastAPI + LangGraph) + Java + MySQL/Milvus，线上主语言模型为 **MiMo 商业托管 API (`mimo-v2.6-flash`)**。

### 1.2 核心探究问题
> **同一个任务、同一批输入，在单张 8GB 消费级笔记本显卡上，用本地开源小模型替换商业云端大模型，能力损耗究竟有多少？能否通过高质量领域微调拉齐差距？**

## 2. 硬件环境硬约束与 3B vs 7B 选型权衡

### 2.1 物理硬件底数
* **GPU**：NVIDIA GeForce RTX 4060 Laptop GPU，物理显存 **8,188 MiB (8.0 GB)**；
* **CPU**：AMD Ryzen 9 7940HX (16核/32线程)，内存 15.2 GB；
* **宿主操作系统**：Windows 11，存在常驻系统桌面渲染底噪（DWM、ShellHost、IDE、Edge 基础显存常驻 **1.35 GB ~ 1.70 GB**）；
* **磁盘硬约束**：C 盘容量紧张，本次实验下载的所有运行时（Ollama）、模型权重、训练虚拟环境 100% 隔离在 `E:\modelTest` 沙箱。

### 2.2 为什么必须全面锁定 3B 级别，而不是 7B？（严谨的显存账本）
在方案设计初期，团队深入评估了 7B 级别模型（如 Qwen2.5-7B）：
* **7B 4-bit 显存账本**：
  * 静态权重：约 4.8 GB；
  * KV Cache (2048 上下文)：约 1.0 GB；
  * 系统底噪：约 1.6 GB；
  * **推理总占用**：$4.8 + 1.0 + 1.6 \approx 7.4\text{ GB}$，已贴死 8.0 GB 硬件红线。在 Windows 机制下，极易触发 NVIDIA 显存向 CPU 共享内存的卸载调度，导致推断速度从 50 token/s 断崖式暴跌至 2~3 token/s；
  * **训练（QLoRA）总占用**：即使开启梯度检查点与 4bit 量化，7B 训练显存至少需 7.8~8.5 GB，叠加 Windows 底噪总需求突破 9.5 GB，在单卡 8GB 上 **100% 触发 CUDA OOM 崩溃**。
* **3B 4-bit 选型结论**：
  * 选定 **`Qwen2.5-3B-Instruct` (4-bit)**：静态权重 2.2 GB，推理占用 3.75 GB；QLoRA 训练峰值实测 5.72 GB（空闲余量 2.04 GB），推理生成速度约 60 token/s（运行时观察值，无日志留痕），**是单卡 8GB 笔记本上唯一能够形成“低成本训练+高吞吐推理”真正闭环的黄金规格**。

## 3. 实验设计与方法论（两个口径，各自内部严格同标尺）

**核心方法学决定：不把"不同标尺"的数字放在同一张表里相减。** 本实验分两个口径，每个口径内部所有臂共享完全相同的 prompt、温度、判分规则与采样次数：

| 口径 | system prompt | 经过主工程 `scope_guard()` | 回答的问题 | 臂 |
| --- | --- | --- | --- | --- |
| **A 工程链路口径** | 主工程完整 planner prompt（32 小类 + 槽位 + 十几条规则） | 是 | 换模型后主链路还能不能用 | MiMo / 3B 裸跑 |
| **B 短契约口径** | `configs/contract_short_with_vocab.txt`：单句 + 完整编码词表 | 否 | 3B 的判别能力 / 微调增益有多少 | MiMo / 3B 裸跑 / 3B+QLoRA |

共同遵守的规矩：
1. **同一套 74 条锚定集**（64 条覆盖 8 大类 32 小类 × 2 种表达风格，10 条域外负样本），与主工程 `eval_queries.py` **逐字一致**；
2. **每例 3 次重复采样**（每臂 222 次推断），报"轮间极差 + 判定级 95% CI + 题目级 95% CI"三个口径，用题目级 CI 判断差异是否显著；
3. **逐条落盘 + 断点续跑**：每臂一个 `checkpoint.jsonl`，报表由 `scripts/build_reports.py` 从原始记录复算（**报表里不允许手写数字**），并记录契约 sha256 证明各臂用的是同一份契约；
4. **防静默代考锁**：本地臂强制 `MIMO_MODEL` 与 `MIMO_MODEL_BACKUP` 同名，从底层阻断异常时悄悄回退到云端 API；
5. **训练与评测契约一致**：v2 适配器的训练 `instruction` 与评测用的契约文件逐字相同（避免 train/infer 不一致）。

## 4. 实验全流程实施实录

### 4.1 阶段 A：74 条锚定集裸跑评测（破除无脑平替神话）
* **执行方案**：在 `E:\modelTest\bin` 部署免安装 Ollama 独立服务，加载 `qwen2.5:3b` 原生权重，运行自动化评测流水线 `phase1_anchor_eval.py`；
* **实测结果**：
  * 云端 MiMo（**同轮**跑，不再是历史数字）：小类准确率 **92.7%**，大类 **96.4%**（74 题 x 3 次采样）；
  * 原生 Qwen2.5-3B 裸跑：小类准确率暴跌至 **58.3%**（**净降幅 -34.4 pt**，远超题目级 CI ±6.4 pt），大类仅 **74.0%**；
  * 尤其在**老百姓口语化表达（Colloquial）**上，裸小模型小类准确率坍塌至 **50.0%（48/96）**，explicit 也只有 **66.7%（64/96）**；
* **阶段 A 结论**：铁的数据证明，未经垂直领域对齐的 3B 级通用小模型，直接替换商业大模型会导致业务严重劣化，平替假设破灭。

### 4.2 阶段 B：数据工程与 5 道防泄露安全隔离
针对阶段 A 暴露的严重断层，启动领域监督微调（SFT）工程：
* **数据源**：从主工程 `ai-module/db/data_cases*.py` 中的 231 条真实历史行政处罚与排查案卷中提取清洗；
* **防泄露防火墙（红线）**：
  * 严禁 74 条基准题库以任何形式流入训练集；
  * 派发专门的数据工程子智能体，运行 5 道 Jaccard 词元重叠度与 Levenshtein 编辑距离检测，剔除相似度 $>0.6$ 的 53 条高风险样本；
  * **独立复核（2026-09-29）**：以字符二元组 Jaccard 重扫 `train_sft.jsonl` × `anchor_74.jsonl`，最大值仅 **0.060**，>0.6 的 **0 条** —— 泄露防火墙成立（口径见 `scripts/build_reports.py`）。
* **最终训练集（`train_sft.jsonl`）**：**256 条**，覆盖全部 32 个小类，每类 **5~9 条**（平均 8 条）——**是全覆盖，但不是"均衡"**。
  * 口径更正（2026-09-29 复核）：该文件字段只有 `instruction / input / output`，**没有 style 字段**，因此"128 条直白 + 128 条口语"的拆分**没有文件证据**；从开头模式看是约 10 种口吻模板（`太悬了！`28 / `今天路过`28 / `你好，我`26 / `向平台反映`25 / `市民热线`23 / `【隐患上报】`23 / `同志你好`23 / `【巡查发现】`22 / `城市运行`21 / `安全隐患`21）。

### 4.3 阶段 B：QLoRA 超轻量高效微调（单卡 8GB 显存闭环）
* **训练环境**：在 `E:\modelTest\venv_train` 建立独立虚拟环境，部署 PyTorch 2.6.0+cu124、Transformers 5.17、PEFT 0.21 与 Windows 原生 BitsAndBytes 0.50.2；
* **超参数配置**：
  * 基座量化：4-bit NF4 (Double Quantization)；
  * LoRA 配置：$r=16, \alpha=32, \text{Dropout}=0.05$；
  * 训练轮数：3 Epochs（共 192 步）；
  * 学习率：$2\times 10^{-4}$，Cosine 退火调度，Warmup 10 步；
  * 显存优化：开启 Gradient Checkpointing，优化器采用 `paged_adamw_8bit`；
* **训练收敛表现（以下全部来自 v2 的实测日志，`logs/train_qlora_v2.log` + `reports/train_qlora_v2_summary.json`）**：
  * 耗时：**844 秒（14 分钟）**，192 步，`train_samples_per_second = 0.91`；
  * Loss：logging 首点 **2.678** → 末点 **0.219**（`train_loss` 均值 **0.523**），中间无发散；
  * 显存峰值：**5.041 GB**（8.0 GB 卡上留出约 3 GB 余量），零 OOM；
  * **踩过并修掉的一个真坑**：契约 1009 字符把上下文顶到 537~851 token，第一版用 `max_length=512` 训练时
    **256/256 条样本全被截断**（日志：`被 512 截断的样本数=256`）——模型根本看不到词表尾部。改成 `max_length=1024` 后
    **0 条被截断**（`min=537 max=851 mean=612.7`），这才是可用的那一版；
  * 产出的适配器：`adapter_model.safetensors` **119,801,528 字节 ≈ 114 MiB**；
  * **历史 v1（7 分钟 / 5,865 MiB / loss 3.866→0.5115）无日志留痕**，属运行时观察值，已被 v2 取代，不再作为结论依据。

### 4.4 阶段 B：终极三臂同标尺复测
将训练产出的 LoRA 权重与基座结合，在**同一套 74 条题库**上跑第三臂。

> **口径声明（2026-09-29 复核后修正，阅读 §5 前必读）**：原复测脚本 `eval_three_arms.py` 与第一/二臂**不是同一把尺** ——

## 5. 实测对比数据矩阵（两个口径，禁止混算）

> **数字来源**：全部由 `scripts/build_reports.py` 从各臂 checkpoint 原始记录复算，汇总见 `reports/CANONICAL_RESULTS.md`。任何数字不得手抄。

### 5.0 两个口径各自的定位（先读这一段）

| 口径 | 是什么 | 回答什么问题 | 能不能拿去做决策 |
| --- | --- | --- | --- |
| **A 工程链路** | 完整走主工程：planner prompt（32 小类 + 槽位 + 十几条规则）+ `scope_guard` + 状态图 | 把这个模型换成 3B，主链路还撑得住吗？ | ✅ **能** —— 这是项目口径，决定选型 |
| **B 短契约** | 一句话 system prompt + 编码词表；**不走图、不走 `scope_guard`**，等价于一次裸 HTTP 调用 | 模型本身的判别能力有多少？微调能买回多少？ | ⚠️ **只能当消融（ablation）参考** —— 产物不能投产，它的契约与主工程不一致 |

> 一句话：**A 是产品口径，B 是实验室口径。** 任何「能不能上生产」的结论只能由 A 得出；B 只用来把「模型能力」与「系统脚手架」两个变量分开看。

### 5.3 由这两个口径能得出的结论（与不能得出的结论）

- ✅ **能得出**：同一个任务（74 题 × 3 次采样、同一 harness、同一天），把主链路的 MiMo 换成 3B 裸跑，小类准确率从 92.7% 掉到 58.3%（**-34.4 pt，超出题目级 CI**）→ 生产链路不能原样替换。
- ✅ **能得出**：在「必须按私有编码词表输出」的极简契约下，256 条领域样本 + 一次 QLoRA 微调，把 3B 从 **50.5%** 拉到 **84.9%**（+34.4 pt）—— 微调**确实**买到了私有标签空间的能力。
- ✅ **能得出（副产品，很值钱）**：同一个云端模型，只把契约从「完整 planner prompt」换成「极简 JSON 契约」，小类准确率就从 92.7% 掉到 74.0%（**-18.8 pt**），JSON 有效率也只有 **83.3%** —— **契约与输出格式的工程价值，和换模型同一量级**。
- ❌ **不能得出**：「微调后的 3B 已经追平商业模型」。跨口径相减（A 的 MiMo 减 B 的 LoRA）是无效比较。
- ❌ **不能得出**：把细粒度准确率提升到 85%+ 需要多少数据 —— n=256 只支持「有显著增益」这个结论，不支持外推。

### 5.4 已知局限（如实登记）

1. **采样实现不同源**：`lora` 臂走 HF `generate`（top_k/top_p 用 transformers 默认），`base`/`mimo` 走 HTTP `max_tokens/temperature` —— 三家采样默认值不是同一个实现，只能保证「温度与长度相同」。
2. **训练/推理契约一致**：v2 适配器的训练 `instruction` 与评测契约**逐字相同**（1009 字符；分词后 537~851 token；**0 条被截断**）—— 不存在 train/infer 契约不一致的问题。
3. **训练集规模小**：256 条、32 类、每类 5~9 条。口语样本的增益（+37.5 pt）**大于**直白样本（+31.2 pt），微调后口语（85.4%）反超直白（84.4%）。
   - ⚠️ 但这**不能**解释成「口语泛化问题被解决」：题集是固定的 64 条，而训练集里本身就有约 10 种口吻模板，微调很可能在**贴合这批口吻**。要证明泛化，必须换一批没见过的口语表达重测（本轮未做）。
4. **n 的尺度**：题目级 CI 在 n=64 时约 ±12 pt、n=192 时约 ±4~7 pt —— 别拿 2~3 pt 的差当结论。
5. **训练 labels 没有屏蔽 prompt 段（v1/v2 都一样）**：`labels = 全部 input_ids`，那 436 token 的恒定契约也在训练目标里，一部分梯度花在「背契约」上，既稀释分类目标又压低 loss（0.5227 含这部分）。下一轮应把 prompt 段 labels 置 -100，且 v1/v2 一起改。
6. **tokenizer 训练/评测不一致（未验证）**：训练用 `use_fast=False`，评测用默认 fast，未逐条比对 74 条输入的 token 序列。
7. **契约里带了 32 个小类的中文 label** → 等于把分类体系直接提示给模型，任务被简化；所以口径 B 的分数不能与口径 A 直接比。
8. **契约文件不能随手重存**：`prompt_sha` 按原始字节算（无尾随换行），编辑器重存会改 sha，而训练的「逐字一致」校验因为 strip 仍通过 —— 静默不一致，需要人工留意。

### 5.5 本实验对「架构价值」的定量证据（同一个模型，两个口径）

| 配置 | 小类准确率 | 说明 |
| --- | ---: | --- |
| 云端 MiMo **走主工程链路**（planner prompt + scope_guard + 图） | **92.7%** | 口径 A |
| 云端 MiMo **裸 HTTP**（一句话契约） | **74.0%** | 口径 B |
| 差 | **-18.8 pt** | 差值全部来自「提示词 + 输出契约 + 范围护栏」这套工程脚手架 |

- 同一个模型、同一批 74 题、同一温度与采样次数，唯一变化就是有没有那套脚手架 —— **脚手架让同一个模型多答对约 19 个点**。这是「为什么要在模型外面套一整套图 / 护栏 / 输出契约」最直接的一次量化。
- ⚠️ 这是**多变量合并效应**（提示词更细 + 输出契约更严 + 有范围护栏），不是单变量消融；要拆开得固定其余变量只改一项（本轮没做）。
- 反过来也成立：**脚手架救不了弱模型**。同样的脚手架套在 3B 裸跑上只有 58.3%（口径 A）—— 所以「为了省 API 费换小模型」靠加提示词/加护栏走不通。
- **对「小模型进主链路」的硬前置（当前不满足）**：v2 适配器按**短契约**训练，直接套主工程 prompt 属于 train/infer 不一致，所以口径 A 下的小模型（含微调版）目前**没有测量结果**。要让小模型真正进主链路，必须先按主工程契约重造 SFT 数据（含 `issues / slots / question / premises_scope` 等字段）再训一轮，然后在**口径 A** 上复测 —— 那时的数字才是项目口径的结论。

## 6. 深度归因与客观瓶颈剖析（实事求是看数据）

在审阅数据时，必须坚持务实求真的态度：**微调在"短契约口径"下把小类从 50.5% 拉到 84.9%（+34.4 pt），并且在同口径下高于云端 MiMo 的 74.0%；但同一个 3B 裸跑在"工程链路口径"下只有 58.3%（MiMo 92.7%）。**换句话说：**微调买到的是"贴合这份契约的能力"，不是"追平商业模型的通用能力"。** 瓶颈的本质成因如下：

### 6.1 为什么微调后的大类准确率（94.3%）能高于同口径的 MiMo（77.1%）？
* **这不是"3B 比商业模型更聪明"，而是"契约适配"**：同一份极简契约下，MiMo 有 **16.7%** 的回答根本没解析成 JSON
  （它习惯输出自由文本），而这些在判分里直接算错；微调臂则是被专门训练来"只吐这一行 JSON"的，**正样本 JSON 有效率 100%**。
* 对照证据：把 MiMo 的契约从"完整 planner prompt"换成"极简 JSON 契约"，它自己的小类准确率就从 **92.7% 掉到 74.0%（-18.8 pt）**。
  → **契约与输出格式的工程价值，和模型规模是同一量级**；这也正好印证主工程的架构选择（格式由代码/提示词约束，模型只管语义）。
* 真正说明"大类能力"的是工程链路口径：3B 裸跑 **74.0%** vs MiMo **96.4%**（差 -22.4 pt）。

### 6.2 微调后还剩哪些短板？瓶颈卡在哪？
1. **样本密度极度稀疏**：
   * 256 条数据平摊给 32 个细分小类，**每类只有 5~9 条**（平均 8 条；训练文件里没有 style 字段，无法拆出"每类几条口语"）；
   * 在小样本冷启动下，模型能记住 32 个编码已属不易，但对群众千奇百怪的隐喻、情绪化口语，注意力特征难以充分泛化
     （口语样本的增益虽大，但题集固定、训练集自带约 10 种口吻模板，**不能证明已泛化**，见 §5.4）。
2. **“混淆小类”的语义天然重叠（两可边界）**：
   * 错题深度诊断显示，失分集中在高度相似的类别对之间：
     * *“楼道堆放旧纸箱遮挡消火栓箱门”* $\rightarrow$ 判定在 `fire_equipment_fault`（消防设施故障）与 `fire_lane_blocked`（消防通道占用）之间摇摆；
     * *“电动车违规飞线充电导致插座打火”* $\rightarrow$ 判定在 `illegal_wiring`（私拉乱接）与 `exposed_wire`（裸露/老化电线）之间摇摆。
   * 商业大模型见过的数十万同类语料能辅助它切开这类边界，而微调臂每类只见 5~9 例，缺乏足够的「对比负样本」敲打。

### 6.3 结构化 JSON 遵循率波动分析
* 原生裸跑时**非空计划率 96.9%（186/192，正样本口径）**，失败的那 6 条是**空计划（JSON/计划解析失败）**，
  **不是网络超时** —— 原报表把它记成「3.6% 超时率(8/222)」是错的：checkpoint 里 `error` 字段全程为空，8 条 `empty_plan` 分布在正样本 6 条 + 负样本 2 条；裸跑还常夹带客套废话（*“好的，为您分析结果如下：```json ... ```”*）；
* 微调后**客套废话被 100% 根除**，短契约口径下 JSON 有效率 **100%（192/192）** —— 这是微调最稳的一项收益；
  对照：同一契约下 MiMo 只有 **83.3%**，裸跑 3B 是 100%（它很会照抄格式，但分类差）。
  → 结论：**"格式合规"和"分类正确"是两种能力**，前者可以靠少量样本 + 契约训练买到，后者才是规模/数据的差距。

### 6.4 判别能力 vs 语言组织能力的架构边界
* **微调专注咽喉**：本次微调主要训练模型的**“判别与抽槽能力”**，这是系统状态图的上游生命线；
* **语言组织依靠 RAG**：下游数千字的正式督办通报，系统架构原则是**“RAG 注入法律事实，Prompt 与代码执行器约束格式，模型负责润色”**。因此小模型无需靠自身参数死记法律条文，大大减轻了容量负担。

## 7. 工业级落地架构：85/15 端云协同混合路由

基于上述实测事实，脱离业务实际鼓吹“小模型全面替代大模型”或悲观认为“小模型毫无用处”都是不成熟的。在真实工业界与政务边缘场景中，推荐采用**端云协同的混合路由模式（Hybrid Routing）**：

```
                        [用户工单自然语言输入]
                                  │
                                  ▼
                   [本地微调 Qwen2.5-3B 推断引擎]
                                  │
                 ┌────────────────┴────────────────┐
                 ▼ (置信度 >= 0.75)                ▼ (置信度 < 0.75 或多模态)
     [85% 高频标准工单]                   [15% 疑难长尾/混淆工单]
                 │                                 │
                 ▼                                 ▼
         [本地直接秒级闭环]                [静默回退云端 MiMo 商业 API]
     (0 推理成本 / 支持离线)                    (高保真长链条兜底)
```

1. **85% 常规工单本地化**：通过置信度过滤，将高确定性工单收敛在本地微调小模型，实现**零 Token 调用成本、毫秒级响应、断网可用与数据物理不出域**；
   * ⚠️ **落地前提（当前不满足）**：三臂的原始输出里**没有可用的置信度字段** —— 主工程 planner 的 `confidence / scope_confidence` 是模型**自报值**、未做校准；微调臂的 JSON 里根本没有该字段。这个闸门要用，必须先做置信度校准（Platt / Temperature Scaling），或先用代理指标（重试一致率、两臂一致率）代替。§8 第 4 问已把它列为待解问题。
2. **15% 疑难工单云端兜底**：低置信度（在两个易混淆类别间概率接近）或带有现场图片的复杂工单，通过网关平滑回退至云端 MiMo；
3. **数据飞轮自我进化**：被云端纠错和人工复核改派的工单自动沉淀为“难例（Hard Negatives）”，定期进行下一轮 LoRA 增量更新。

## 8. 提请第三方专家模型（Reviewer）重点审阅的问题清单

请审阅本报告的第三方模型 / 技术专家，重点围绕以下技术命题提供专业评估与挑刺：

1. **实验方法学效度（Methodology Validity）**：
   * 在小样本（74 条测试集、256 条微调集）硬约束下，我们采用「每例 3 次重复采样 + 防泄露隔离」的评测协议，
     并且用了**两个口径**（工程链路 / 极简契约）分开报数、用题目级二项 CI 判断显著性。这个设计是否存在隐蔽的方法学漏洞？
     （已知局限已列在 §5.4：采样实现不同源、口语泛化未验证、n 只有 64。）
2. **小样本冷启动突破瓶颈（Few-shot SFT Ceiling）**：
   * 当前 256 条样本下，**口径 B** 的小类准确率 84.9%、大类 94.3%；但**口径 A（主链路 planner 契约）未测**，
     因为 v2 适配器是按「短契约」训练的，直接套主工程 prompt 属于 train/infer 不一致。
     若要在主链路上用，是否**必须**先按主工程契约重造 SFT 数据（含 issues/slots/question 字段）再训一轮？
     在不能大规模人工标注的前提下，优先推荐何种数据工程手段（大模型反思回译改写、CoT 辨析微调、轻量 DPO）？
3. **8GB 显卡下的极端参数优化（Hyperparameter Optimization）**：
   * 针对 QLoRA 当前参数（Rank 16, Alpha 32, LR 2e-4, 3 Epochs），是否有进一步压缩显存或提升表征容量的超参数组合？
4. **混合路由（Hybrid Routing）的阈值界定**：
   * 在工程落地中，基于 3B 模型输出的 Logits / Softmax 概率作为置信度分流阈值，是否存在温度敏感或校准度偏差（Over-confidence）问题？业界通常如何对小模型进行置信度校准（Platt Scaling / Temperature Scaling）？
5. **3B vs 7B 权衡的合理性**：
   * 结合前述显存账本，我们在单卡 8GB 笔记本上果断放弃 7B、全面锁定 3B 的决策，是否符合严谨的工程与商业落地规范？
